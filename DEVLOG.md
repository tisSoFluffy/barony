# Barony — Development Ledger

## How to use this ledger
- **Append-only.** New entries go at the top of the Log, dated, with a short scope line.
- Each entry records: **what changed**, **why**, **files touched**, and **how to verify**.
- Claude: consult this file at the start of a session before re-deriving project state; append an entry after each completed work block. Keep entries terse — link to code rather than duplicating it.
- Verification commands live in the Reference section; don't repeat them per-entry.

## Project agents (.claude/agents/)
Persistent Sonnet subagents, each pre-loaded with this project's conventions. Every agent reads this ledger before working and appends its own Log entry when done.
| Agent | Owns |
|---|---|
| `sprite-wrangler` | Gemini sprite/texture pipeline: generate → clean → slice → import → wire |
| `gameplay-engineer` | Player/Enemy/Projectile/CombatJuice, skills, XP, headless test suites |
| `level-artist` | DungeonTile/TileLevel/LevelDressing, lighting, atmosphere, dressing |

| Task | Command |
|---|---|

| Slice sheets → frames | `python3 tools/slice_sprites.py` (add entries per character first) |
| Generate SpriteFrames resources | `Godot --headless --path godot -s tools/gen_spriteframes.gd` (run after slicing — rebuilds `res://frames/<char>.tres` from CHAR_CONFIG; idempotent) |

| Headless asset import | `Godot --headless --editor --import --quit` (after adding new textures) |

**Constraints:** GUI processes (Chrome bots, game window) must run as *foreground* Bash — backgrounded tasks get no macOS window session. Gemini images carry a sparkle watermark bottom-right; patch before use (see scratchpad patch_watermark.py pattern).

**Sprite pipeline:** SPRITE_PROMPTS.md (prompts) → gemini_bot.py (generate) → slice_sprites.py (frames to `godot/sprites/sliced/<char>/`) → SpriteFactory.gd CHAR_CONFIG (pixel_size: 0.002 small / 0.0015 medium / 0.0008 boss) → Dungeon.gd spawn pool.

**Known-flaky tests (physics timing; protocol: run 3×, 2/3+ passes = flake, 0/3 = regression):** test_combat (~1 in 6) and test_weapons' "mace staggers in fewer hits" case (rarer). A hardening pass is on the ideas bench.

### 2026-07-09 — First real 3D-modeled prop: potion bottle pickups (health/mana) via Blender MCP
- **First non-sprite mesh asset in the game.** Barony's items are entirely code-built sprite/primitive visuals (`GroundItem._build_visuals`: glow SphereMesh + Label3D icon). Modeled a stylized potion bottle (glass body/neck + cork + glowing liquid) in Blender via the live blender-mcp connection, exported two color variants as `.glb` (red=health, blue=mana), wired them into the existing pickup as a straight visual swap.
- **Export pitfall (cost 3 iterations): Blender parent/child location + `matrix_parent_inverse` doesn't zero out the way you'd expect.** The source scene had `PotionBottle` (empty) and its 4 mesh children all sitting at world `(-3, 0, 0)`, with each child's own `location` field *also* reading `(-3, 0, 0)` (parenting done without compensating `matrix_parent_inverse`, unusual authoring). Naively zeroing `dup_empty.location` after duplicating (attempt 1) left the original offset baked into the glTF root transform — mesh rendered 10+ units from origin, invisible-tiny in Godot regardless of camera distance. Zeroing both parent AND child `location` fields (attempt 2) left a residual ~0.3m offset — parent-inverse math doesn't cancel cleanly under repeated duplication. **Fix:** bypass `location`/`parent_inverse` entirely — read each object's absolute `matrix_world` (always correct regardless of parenting setup), do the recentering/rescaling as an explicit `Matrix.Translation`/`Matrix.Scale` composed against that world matrix, `parent = None`, assign `matrix_world` directly, then `transform_apply`. Robust to whatever parenting quirks the source file has. **Lesson for any future Blender→glTF export: verify the exported root's transform is identity and the mesh AABB is centered near origin before trusting it in-engine — don't assume `location = (0,0,0)` on the object you're exporting means the baked-in offset is zero.**
- **Scale:** source bottle was modeled 1.2×1.2×1.6m (prop/furniture scale) — exported at `scale_factor=0.125` to land at a real potion size (~0.15-0.2m tall), matching the previous glow-sphere's footprint (radius 0.18).

### 2026-07-08 — Fix: character faced left at rest after moving right; sword swing lagged the hand by a phase
Two user-reported bugs, both reproduced on camera via DevRigShot before touching code, both fixed and re-verified by capture. Root causes were independent.

**Bug 1 — facing mapping inverted (visual only).** `Player._update_anim`'s flip_h mapping (`screen_x < -0.05 → flip_h=true`, `> 0.05 → flip_h=false`) silently assumed the unflipped warrior art faces screen-RIGHT. **Empirical finding:** it doesn't — DevRigShot captures with `_facing_dir` forced to `(1,0,0)` and `(-1,0,0)` (see below; the rig's old `face_left` arg was itself broken, see Tooling note) show the unflipped sheet's walk cycle stepping and sword-trailing toward screen-LEFT, shield on screen-right — the art was drawn facing left. The old mapping therefore flipped away from screen-right and displayed the natively-left-facing art exactly when the player moved right, i.e. "faces left after moving right," and the flip never corrected because `_facing_dir` (not velocity) drives it and persists at rest (2026-07-02 fix) — so the wrong-facing pose was also the one that stuck.
- **Fix (`scripts/Player.gd:154-162` new `ART_FACES_LEFT := true` const, `:849-856`):** flip comparisons now read `flip_h = ART_FACES_LEFT` (facing right) / `not ART_FACES_LEFT` (facing left) instead of bare booleans — self-documenting and reversible if the art is ever re-baked facing right.
- **Verified:** re-captured idle/walk/attack sword + spear at both facings post-fix — moving right now mirrors the art (shield screen-left, weapon screen-right, forward lean to the right); moving left keeps the original unflipped pose; weapon overlay (which mirrors off `_parent_sprite.flip_h`) still sits in the correct hand in both facings for both weapons, no floating/misalignment introduced. `--rig-yaw=0.8` spot-check with greatsword: yaw invariance (2026-07-08 earlier fix) survives. `_facing_dir` / melee aim untouched — confirmed visual-only.

### 2026-07-08 — Fix: weapon overlay floats/disappears as the player turns (camera-plane manual billboard)
- **Root cause (confirmed via yawed rig captures):** the body `AnimatedSprite3D` uses `BILLBOARD_FIXED_Y` — its VISUAL always faces the fixed camera regardless of the parent `CharacterBody3D`'s node yaw — but `WeaponOverlay` (`scripts/WeaponOverlay.gd`) was a plain non-billboarded `Sprite3D` child placing itself via LOCAL `position`/`rotation_degrees.z`. `Player._physics_process` (`scripts/Player.gd:428`, `rotation.y = lerp_angle(rotation.y, target_angle, 12.0*dt)`) rotates that parent node toward movement — the overlay's local offset rotated WITH the node while the body's visual didn't, so the weapon orbited the body as heading changed: near yaw 0.8 rad it swam out in front of the body edge-on/detached; near yaw 2.4 rad it foreshortened to an near-invisible sliver at the hip. Previous rig-shot tuning (2026-07-02 entries) never varied `player.rotation.y`, so this never showed up in captures.
- **Reproduced first:** added a permanent `--rig-yaw=<rad>` arg to `scripts/autoload/DevRigShot.gd` (`_rig_yaw`/`_has_rig_yaw`, applied to `_player.rotation.y` once before framing/stepping) and captured idle/walk/attack at yaw 0.8 and 2.4 — confirmed both failure modes (floating-detached at 0.8, near-invisible-edge-on at 2.4) before touching the fix.
- **Fix — `WeaponOverlay.gd`:** `top_level = true` (was `false`); `_process` now builds the overlay's full `global_transform` every frame from fixed camera-space axes instead of local `position`/`rotation_degrees`, completely bypassing the parent node's yaw — the same trick `BILLBOARD_FIXED_Y` does internally, done by hand so a per-anchor roll can still be baked in:
